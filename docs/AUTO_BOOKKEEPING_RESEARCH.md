# vivo 自动记账调研与参考项目

更新日期：2026-08-20

## 结论先行

用户期待的体验是可实现的，但第三方 App 很难完全复刻 vivo 系统钱包：

- 能可靠实现：手动记账、通知识别、候选账单、去重、自动分类、报表、账单导入；
- 部分可实现：微信和支付宝在通知中明确提供金额的付款场景；
- 无法保证：不发系统通知、通知隐藏金额、免密扣款、部分退款/还款、微信部分收款场景；
- 不应承诺：100% 无感、100% 准确、覆盖支付应用每次版本变化。

第一版应把目标定为“通知自动识别 + 待确认”，再通过真机样本逐步提高覆盖率。

## 1. vivo 钱包展示了什么

vivo 官方社区公开的使用路径是：

```text
钱包 → 记账 → 设置 → 自动记账
```

用户可以打开短信、微信、支付宝、云闪付和钱包等账单来源。记账结果提供：

- 按时间排列的收支明细；
- 折线图、饼图等报表；
- 日、周、月收支桌面组件；
- 自动分类和手动补账。

官方说明也列出了不能稳定自动记录的情况，例如部分免密支付、自动扣款、退款、信用卡/花呗还款、余额宝转入转出、微信人脸支付和部分收款场景。这证明成熟的系统级产品也必须保留手动补录和账单导入。

公开展示：

- [vivo 官方社区：春节记账，一目了然](https://bbs.vivo.com.cn/newbbs/thread/38202713)
- [vivo 官方社区：vivo 钱包，生活全包](https://bbs.vivo.com.cn/newbbs/thread/38503419)

vivo 没有公开这项功能的内部实现。由于它是手机厂商的系统钱包，可能拥有普通第三方 App 得不到的系统集成能力；这是基于产品身份和能力差异做出的判断，不是 vivo 官方披露的技术结论。

## 2. 可查看的开源实现

### 2.1 简记账

地址：[jinyule/bookkeeping](https://github.com/jinyule/bookkeeping)

这是最接近本项目目标的参考：界面和核心流程明确参考 vivo 钱包，使用 Kotlin、Compose 和 Room，实现了手动账单、报表、CSV 导入、通知识别和候选账单。

值得参考：

- vivo 风格的信息架构和记账流程；
- 微信、支付宝、云闪付、vivo Pay 的解析器分层；
- 原始文本脱敏和本地保存；
- 真机验证报告和解析回归样本；
- 对无障碍误识别自身页面的修复案例。

不能直接照搬：

- 仓库没有可公开下载的 Release 和公开截图；
- 无障碍识别涉及较高隐私、兼容性和上架风险；
- 参考其思路前必须检查许可证和具体代码质量。

### 2.2 无感记账

地址：[DykiSensei/seamless-bookkeeping](https://github.com/DykiSensei/seamless-bookkeeping)

这个项目展示了完整 MVP 组成：支付宝/微信通知、银行短信、规则分类、去重、账单列表、报表、预算和国产系统后台设置指南。

最有价值的是它明确记录了限制：通知文本会变化、部分微信场景没有通知、国产系统可能杀后台服务、vivo 对第三方无障碍服务可能存在兼容问题。它声称解析覆盖率约 80%，该数字只是项目作者的自述，不应直接作为本项目指标。

需要警惕：

- 它请求短信和无障碍权限，正式上架前需要重新评估；
- “同来源同金额 60 秒去重”过于简单，可能误伤连续等额消费；
- README 中部分兼容性结论来自有限设备实测，不能外推到全部手机。

### 2.3 其他演示

- [2144474967/AutoAccounting](https://github.com/2144474967/AutoAccounting)：较简单的通知识别示例，适合理解最小流程，不建议直接作为生产底座。

## 3. 我们应采用的实现路线

```text
第一层：通知监听
  微信/支付宝通知中存在金额 → 解析为候选账单

第二层：账单导入
  微信/支付宝 CSV 或结构化账单 → 批量导入和去重

第三层：手动快速补账
  自动识别失败 → 预填时间和来源，用户只补金额/分类

暂缓：短信、无障碍、OCR
  分别涉及商店审核、隐私风险、兼容性或较高开发成本
```

自动捕获后先生成“待确认账单”。经过真实样本验证后，用户可以为某个来源和规则单独打开“直接入账”。所有自动账必须显示来源、解析依据，并支持一键撤销。

## 4. MVP 展示流程

第一版原型应完整演示以下闭环：

1. 用户进入自动记账页并开启通知使用权；
2. 用户选择微信和支付宝来源；
3. 测试通知到达；
4. App 显示“发现一笔 ¥18.80 的餐饮支出”；
5. 用户确认或修改分类；
6. 首页、明细和月度报表同步更新；
7. 相同通知再次送达不会重复记账；
8. 用户可以撤销刚刚的自动入账。

这个流程比一开始追求所有真实支付场景更适合作为可测试、可演示的第一个版本。

## 5. 研究验证清单

在正式实现微信/支付宝解析器前，需要用户在自己的手机上采集脱敏样本。每个样本只保留：

- 来源应用；
- 通知标题和正文格式；
- 支出/收入/退款/转账场景；
- 是否出现明确金额；
- 手机品牌、系统版本和应用版本。

提交样本前删除姓名、手机号、完整卡号、订单号、真实商户和真实金额。代码仓库只保存脱敏测试样本，绝不提交真机数据库、完整通知历史、截图账号信息或签名密钥。
